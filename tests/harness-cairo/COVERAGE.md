# What the cairo harness proves (and what it doesn't)

cairo is tbBlob's second real library (D-055), after libgit2. Where libgit2 is a large API of
handles, strings and callbacks, cairo adds graphics: doubles everywhere, structs that cairo fills
(`cairo_matrix_t`, `cairo_text_extents_t`), a union of anonymous structs (`cairo_path_data_t`),
types from headers outside cairo's folder (Windows GDI, FreeType), a second DLL
(`cairo-script-interpreter-2.dll`), and a header tbBlob cannot read (`cairo-dwrite.h`, C++ only,
D-059). This harness calls cairo 1.18.4 (vcpkg) through the generated bindings on **win32 and
win64**; see `tests\harness-fixture\COVERAGE.md` for the synthetic library that holds every
construct once, and `tests\harness-libgit2\COVERAGE.md` for libgit2.

The bindings are generated by `build-project.ps1` from `cairo.h` plus the backend headers
(`--also`): pdf, ps, svg, script, tee, win32, ft, script-interpreter and dwrite (skipped and
reported). That gives 409 declares for `cairo-2.dll` and 10 for `cairo-script-interpreter-2.dll`;
the integration test `Tests_EndToEnd.CairoCounts` checks those counts against the export tables.

## How it checks

- Every check is a `PASS|FAIL` line in `results\results-<arch>.txt`; each group runs under its own
  error handler, so one error does not stop the run.
- Values are checked by what cairo does with them: a pixel read back from the surface's memory,
  a file's first bytes, a matrix applied to a point, a status code.
- Temp files go to `%TEMP%\tbBlob-cairo-<arch>.*` and are deleted afterwards.

## Coverage by check group

| # | Group | What it proves |
|---|---|---|
| 0 | Loading | The generated `Cairo_Loader.Load(bin)` loads both DLLs from this architecture's vcpkg `bin` (D-053); `cairo_version() = 11804` |
| 1 | Layout | `Cairo_LayoutCheck.LayoutMismatches()` is empty: every generated Type, cairo's own and the imported outside ones (`tagLOGFONTW`, FreeType's records), matches CastXML on both architectures |
| 2 | Image surface | Enum argument, handle returns, `Double` arguments; a returned `LongPtr` (`get_data`) plus `get_stride` read with `vbaCopyBytes`: the filled pixel is opaque red, another is transparent |
| 3 | Paths | A returned struct pointer (`cairo_copy_path` → `cairo_path_t`) read into the Type; its array of `cairo_path_data_t`, a union of two anonymous structs, read element by element through the generated accessors `header` (type, length) and `point` (x, y), D-068 (each element is copied into a variable first: calling a Type's method directly on an array element is not safe; it was shown to crash when tested on tB BETA 1011, D-069); `cairo_path_destroy` taking cairo's pointer through its `ByRef` parameter (`ByVal pp`) |
| 4 | Structs filled by cairo | `ByRef cairo_text_extents_t` and `ByRef cairo_matrix_t` out-parameters; `ByRef Double` in/out (`cairo_matrix_transform_point`); `cairo_rectangle_list_t` with its pointer-plus-count array of `cairo_rectangle_t` |
| 5 | PNG | UTF-8 file name; a PNG written, read back (same size and pixel); `cairo_surface_write_to_png_stream` with a `CDecl` function as the `cairo_write_func_t` delegate, called by cairo with its data: the byte count equals the file's and the PNG signature arrives first |
| 6 | PDF and SVG | The `--also` backend headers' functions (`cairo_pdf_surface_create`, `cairo_svg_surface_create`): files start `%PDF` / contain `<svg` after `cairo_surface_finish` |
| 7 | Win32 | Outside types (D-054, D-058): an `HDC` (handle alias) from a hand-declared `CreateCompatibleDC` passed to `cairo_win32_surface_create`; a `tagLOGFONTW` filled in tB and passed `ByRef` to `cairo_win32_font_face_create_for_logfontw`; text extents in that font |
| 8 | FreeType | `FT_Library` / `FT_Face` (outside pointer typedefs, generated as aliases) from hand-declared FreeType calls on `freetype.dll`; `cairo_ft_font_face_create_for_ft_face`; text extents in that font |
| 9 | Script interpreter | The second DLL's functions; `cairo_script_interpreter_hooks_t` with a `CDecl` function in its `surface_create` delegate field; cairo calls it with `Double` and enum arguments and uses the surface it returns; the script paints it red |
| 10 | Errors | `cairo_status_to_string` (returned `const char*`, read as UTF-8); a negative size gives `CAIRO_STATUS_INVALID_SIZE` |
| 11 | DirectWrite | The hand-written `cairo_dwrite.twin` (D-059) for the header tbBlob skips: an `IDWriteFontFace` made through hand-declared `DWriteCreateFactory` and vtable calls, passed as `LongPtr /* IDWriteFontFace */`; `set_measuring_mode(GDI_CLASSIC)` reads back; text extents in that font |

Task 30.1 numbers the runtime groups 1–10; here they follow the boundary (0) and layout (1)
checks of task 29, so they are 2–11.

## Not covered

- **The PostScript, tee and script (writer) surfaces.** They are generated and in the layout
  check, but not called. They use the same forms as PDF and SVG.
- **Callbacks on cairo's own threads.** cairo calls back on the caller's thread in everything
  tested here. Threads are covered by the tbfixture harness (group 18).
- **Leaks.** Every object is destroyed, but nothing measures whether cairo freed it.
- **Most of the API.** 48 of the 419 generated functions are called (plus 3 of the 5 hand-written
  `cairo_dwrite_*`). tbBlob generates mechanically, so
  what matters is that every *kind* of binding is exercised, which the table above and the other two
  harnesses cover.

## Re-running

`powershell -ExecutionPolicy Bypass -File tests\run-all.ps1` regenerates the bindings when tbBlob
was rebuilt and runs this harness on both architectures. It needs cairo installed by vcpkg on both
architectures; see `cairo\README.md`.
