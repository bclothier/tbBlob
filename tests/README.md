# tests\

Everything that proves tbBlob works, apart from the unit tests compiled into tbBlob itself
(`Source\Sources\Tests\`). The aim is the PRD's goal: generated bindings that compile and **run**
correctly on win32 and win64. A clean regeneration is not enough on its own, so most suites call
real DLLs through the generated code.

## Running everything

```
powershell -ExecutionPolicy Bypass -File tests\run-all.ps1
```

`run-all.ps1` is the full regression run (the task list's "full suite"). It runs these in order and
prints a `PASS`/`FAIL` line for each at the end. The exit code is 0 only if every suite passed:

| # | Suite | What it proves |
|---|---|---|
| 1 | `import.ps1` | `tbBlob.twinproj` is rebuilt from `Source\`, the source of truth (D-010) |
| 2 | stale-build check | `Build\tbBlob_win64.exe` is newer than every file in `Source\`. If not, the run stops with exit 2 and asks for a recompile; it never reports on old code |
| 3 | `tbBlob --self-test --integration` | tbBlob's own tests: unit tests, then integration tests that run CastXML and MSVC on `fixture-c` and libgit2 |
| 4 | `fixture-c\build.ps1`, `fixture-c\test_build_errors.ps1` | The C fixture library builds for x86 and x64, its C tests pass, its exports are as expected, and a missing toolchain is reported clearly |
| 5 | harness-fixture win32 / win64 | Generated bindings for `tbfixture.dll`, called from twinBASIC (see [harness-fixture\COVERAGE.md](harness-fixture/COVERAGE.md)) |
| 6 | harness-libgit2 win32 / win64 | Generated bindings for libgit2 1.9.1 doing real work on test repositories (see [harness-libgit2\COVERAGE.md](harness-libgit2/COVERAGE.md)) |
| 7 | `verdict.ps1 -SelfTest` | The verdict script judges its fake inputs correctly |
| 8 | `tools\package.ps1 -SelfTest` | The distributable: layout, licences, docs, `tbBlob --check` with the bundled CastXML, a generation from the package |

A full run takes a few minutes.

## Manual steps

twinBASIC projects are compiled in the IDE by hand; no script can do it. `run-all.ps1` detects a
stale or missing EXE and says which project to compile, for which architecture:

- **tbBlob**: `tests\import.ps1`, then open `tbBlob.twinproj` and compile **win64**.
- **A harness**: `tests\harness-<name>\build-project.ps1` (`run-all.ps1` runs it for you when tbBlob
  changed), then open `tests\harness-<name>\harness_<name>.twinproj` and compile it as **win32 and
  win64**. A harness needs a recompile only when the generated code actually changed:
  `harness-sync.ps1` copies only modules whose content changed and stamps the bindings with tbBlob's
  SHA-256.

## First run on a fresh clone

Expect failures until the manual steps are done; they are not defects. A first `run-all.ps1` on a
clean clone builds the fixture DLLs and generates the harness projects itself, but cannot compile
twinBASIC, so the harness suites (5 and 6, win32 and win64) report `STALE ... does not exist` and a
large share of the checks are missing. Compile each harness as win32 and win64 in the IDE (see above)
and run it again. Nothing depends on the spike output in `spikes\`: every test generates what it needs
(libgit2 needs only its vcpkg install, [libgit2\README.md](../libgit2/README.md)).

## What's here

| Path | Purpose |
|---|---|
| `run-all.ps1` | The full regression run, above |
| `import.ps1` | Rebuilds `tbBlob.twinproj` from `Source\` with the import/export tool (`tools\impexp\`, see [tools\README.md](../tools/README.md)). Run it before every compile of tbBlob |
| `fixture-c\` | **tbfixture**, a small C library written to exercise every C construct tbBlob must handle: structs, unions, bitfields, packing, callbacks, variadics, stdcall, macros, case collisions, threads, library-allocated memory. `tbfixture.h` (plus `tbfixture_sys.h`, which it does not include, for `--also`), `tbfixture.c`, `tbfixture.def`, `test_tbfixture.c` (C-side tests). `build.ps1` builds `bin\win32\` and `bin\win64\` |
| `harness-fixture\` | twinBASIC project that calls `tbfixture.dll` through the generated bindings and checks every result. `Sources\` is hand-written; `bindings\` and `project\` are generated |
| `harness-libgit2\` | The same for libgit2 from `libgit2\` (see [libgit2\README.md](../libgit2/README.md)). `setup_fixture.ps1` creates its test repositories with `git.exe` |
| `harness-sync.ps1` | Shared by both `build-project.ps1` scripts: content-based sync and the tbBlob stamp |
| `verdict.ps1` | Computes the PRD's success metrics from the real artifacts and prints the verdict (see `tasks\verdict-castxml-ffi-generator.md`). `-SelfTest` runs it against `testdata\verdict\` |
| `testdata\` | Inputs for tbBlob's unit tests: CastXML snapshots of tbfixture (`fixture\`, regenerated by `regen-fixture-xml.ps1` after `tbfixture.h` changes; they hold `{REPO}` where CastXML wrote the clone's root, and the tests substitute the real root through `SelfTest.Fixture`, so the clone can be anywhere, D-051), small hand-written XML (`model\`, `typemap\`), macro dumps (`macros\`), and the verdict cases (`verdict\`) |

Generated folders (`bin\`, `Build\`, `bindings\`, `project\`, `results\`, `fixture\`, `*.twinproj`)
are gitignored. Each harness writes `results\results-<arch>.txt`, one `PASS`/`FAIL`/`INFO` line per
check, ending with an `INFO 0.summary` line. A missing summary means the harness crashed.

## What it needs

See [To run the tests](../docs/SETUP.md#to-run-the-tests) in `docs\SETUP.md`. In short: Visual
Studio 2022 or the Build Tools with the C++ workload, the twinBASIC IDE, CastXML in `CastXML\` and
libgit2 (x64 and x86) in `libgit2\`, both installed with vcpkg, and `git.exe` on `PATH`.

## Adding a test

- **Generator behaviour**: a test in the matching `Source\Sources\Tests\Tests_*.twin` module. Use a
  `testdata\` input, or a construct added to `fixture-c\tbfixture.h` (then run
  `regen-fixture-xml.ps1`).
- **Runtime behaviour** (does the generated code actually work when called): add the C function to
  `fixture-c` with a C test, then a check in `harness-fixture\Sources\Harness.twin`, and update its
  `COVERAGE.md`.
